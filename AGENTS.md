# AGENTS.md

Guidance for AI coding agents working in this repository.

## What this repo is

`provider-ovh` is a [Crossplane](https://crossplane.io/) provider generated by
[Upjet](https://github.com/crossplane/upjet) on top of the
[OVHcloud Terraform provider](https://github.com/ovh/terraform-provider-ovh).
Almost all Go code under `apis/` and `internal/controller/` is **generated**.
The hand-written surface is small: `config/`, `internal/clients/`, `cmd/`, `examples/`.

**Rule of thumb: never edit a `zz_*` file.** Change `config/`, then regenerate.

## Commands

The build system is the `crossplane/build` git submodule mounted at `build/`.
If `make` fails with missing includes, the submodule is not initialised:

```bash
make submodules          # git submodule update --init --recursive
make vendor              # go mod download / vendor deps (vendor/ is gitignored)
```

Day-to-day:

```bash
make build               # builds cmd/provider and cmd/generator
make test                # unit tests (go test ./...)
make lint                # golangci-lint, config in .golangci.yml
make reviewable          # generate + lint + test — run before opening a PR
make check-diff          # fails if `make generate` leaves uncommitted changes (CI gate)
make run                 # run the controller out-of-cluster against current kubecontext
```

Single test:

```bash
go test ./config/... -run TestPostgresqlUserIdentifierFromProvider -v
```

Code generation (needs network: downloads Terraform, fetches the provider schema,
sparse-clones the upstream docs):

```bash
make generate            # full pipeline (schema.json + pull-docs + go generate)
go run cmd/generator/main.go "$PWD"   # generator only, reuses existing config/schema.json
```

End-to-end (spins up a kind cluster, installs Crossplane, deploys the local xpkg):

```bash
make local-deploy
UPTEST_EXAMPLE_LIST="examples/cluster/kubernetes/cluster.yaml" make uptest
make e2e                 # local-deploy + uptest
```

Go toolchain is pinned by `GO_REQUIRED_VERSION` in the `Makefile` (currently 1.25.6).

## Architecture

### Two API surfaces from one config

The provider ships **two parallel API sets**, both generated from the same
resource configuration:

| Surface | Root group | Source tree | Crossplane model |
|---|---|---|---|
| cluster-scoped | `ovh.edixos.io` | `apis/cluster/`, `internal/controller/cluster/`, `config/cluster/` | legacy (v1) MRs |
| namespaced | `ovh.m.edixos.io` | `apis/namespaced/`, `internal/controller/namespaced/`, `config/namespaced/` | modern (v2) MRs |

`config/provider.go` builds both: `GetProvider()` (cluster) and
`GetProviderNamespaced()` (namespaced). `cmd/provider/main.go` registers both
controller sets against the same manager, sharing one `OperationTrackerStore`.

**`config/cluster/**` and `config/namespaced/**` are byte-identical copies.**
Any change to a resource configurator must be applied to both trees, and the new
`Configure` function must be added to *both* lists in `config/provider.go`.

### Two reconciliation architectures

Upstream OVH resources are split between the Terraform Plugin SDK and the Plugin
Framework, and this provider drives each differently — see `config/external_name.go`:

- `TerraformPluginSDKExternalNameConfigs` — SDK resources, reconciled through the
  Terraform CLI / SDK path.
- `TerraformPluginFrameworkExternalNameConfigs` — Framework resources, reconciled
  natively over gRPC against an in-process `ovh.OvhProvider{}` instance.
- `CLIReconciledExternalNameConfigs` — currently empty.

**These maps are also the include list.** `TerraformPluginSDKResourceList()` and
`TerraformPluginFrameworkResourceList()` derive the regexes passed to
`WithIncludeList` / `WithTerraformPluginFrameworkIncludeList`. A Terraform
resource absent from both maps produces no CRD, no types, no controller.

### External names

OVH Terraform IDs are usually composite (`serviceName/id`,
`serviceName/clusterID/userID`, …), so many resources need a custom
`config.ExternalName` with a `GetIDFn` that rebuilds the ID from spec fields,
plus `DisableNameInitializer: true`. Reusable ones live at the top of
`config/external_name.go` (`kubeIdentifierFromProvider`,
`subnetIdentifierFromProvider`, `postgresqlUserIdentifierFromProvider`, …).

Two conventions matter:

- When `externalName` is empty the resource does not exist yet — return `""`,
  not a half-built ID.
- `postgresqlUserIdentifierFromProvider` goes further and calls the OVH API
  (`newOVHClient` / `lookupPostgresqlUserID`) to recover orphans created when a
  Terraform create succeeded server-side but failed to report back.

`config/external_name_test.go` guards these composite IDs;
`TestSDKMapBindingsRestored` exists specifically to catch a regression where an
entry is silently reverted to `config.IdentifierFromProvider`.

### Per-group resource configuration

`config/{cluster,namespaced}/<group>/config.go` holds `Configure(p *config.Provider)`
functions that call `p.AddResourceConfigurator("ovh_...", ...)` to set:

- `r.ShortGroup` + `r.Kind` — these decide the API group and Kind
  (`ovh_cloud_project_kube` → `kube.ovh.edixos.io/v1alpha1, Kind=Cluster`).
- `r.References[...]` — cross-resource references; `Extractor` points at a
  function path such as `config/common.PrivateNetworkOpenStackIdExtractor()`.
- `r.UseAsync = true` — for long-running OVH operations (kube clusters, node
  pools, cloud projects, registries).

Directory names here are Terraform-flavoured (`config/cluster/dedicated_server/`)
while the generated API group is the `ShortGroup` (`apis/cluster/dedicatedserver/`).

### Credentials

`internal/clients/ovh.go` resolves the `ProviderConfig`, extracts the secret and
unmarshals `OVHCredentials` (JSON). Two auth modes:

- application key / secret / consumer key (legacy), and
- OAuth2 `client_id` / `client_secret`, whose tokens are cached per
  `providerConfig:namespace/secret` key in `internal/clients/oauth_token_cache.go`.

The same `TerraformSetupBuilder` serves both API surfaces and also attaches a
fresh `ovh.OvhProvider{}` as `ps.FrameworkProvider` for Framework resources.

## Adding or changing a resource

1. Add the Terraform resource name to the right map in `config/external_name.go`
   (SDK vs Framework — check how upstream implements it), with an appropriate
   `config.ExternalName`.
2. Add or extend `Configure` in `config/cluster/<group>/config.go` **and**
   `config/namespaced/<group>/config.go` (identical content).
3. If the group is new, register both `Configure` functions in `config/provider.go`
   (`GetProvider` and `GetProviderNamespaced`).
4. Regenerate: `go run cmd/generator/main.go "$PWD"`, or `make generate` for the
   full pipeline including CRDs and deepcopy.
5. Commit all generated output — `apis/**/zz_*.go`, `internal/controller/**/zz_*.go`,
   `package/crds/*.yaml`, `examples-generated/`. CI's `check-diff` fails otherwise.

`apis/generate.go` drives generation: it deletes existing `zz_*` files and
`examples-generated/`, runs the Upjet generator, then `controller-gen` (deepcopy +
CRDs into `package/crds`) and `angryjet` (crossplane-runtime methodsets). The
Terraform docs scraper step is currently disabled; `config/provider-metadata.yaml`
is committed as-is.

## Bumping the Terraform provider

Change both `TERRAFORM_PROVIDER_VERSION` and `TERRAFORM_NATIVE_PROVIDER_BINARY`
in the `Makefile`, bump `github.com/ovh/terraform-provider-ovh/v2` in `go.mod`,
`go mod tidy`, then `make generate` and `make build`. CI runs `make crddiff`
(breaking CRD schema changes) and `make schema-version-diff` (native state schema
version changes) on PRs — expect to react to their output.

## Conventions

- Examples: `examples/` is hand-written and is what uptest consumes;
  `examples-generated/` is generated output — don't hand-edit it.
- Commits must be DCO signed off (`git commit -s`); branch off `main`.
- Release flow, marketplace extension assets under `extensions/`, and SBOM
  regeneration are described in `CONTRIBUTING.md` and `README.md`.
